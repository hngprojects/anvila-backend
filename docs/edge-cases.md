## Same-email account collision policy

### What we do

When the GitHub OAuth callback resolves to a verified email address that already belongs to a local user, and that user does not already have this GitHub identity linked, the backend does NOT log the user in. It performs an interactive proof-of-control step:

1. Mint a one-shot link-confirmation token (32 random URL-safe bytes; sha256 of the raw value is persisted in `oauth_link_tokens` with `expires_at = now + 30 minutes`).
2. Schedule an email to the verified address containing a click-through link that includes the raw token.
3. Return HTTP 200 with `ApiResponse[LinkConfirmationData]` (`link_confirmation_required: true`, plus a masked email hint like `o***@e***.com`). No access token, no refresh-token cookie.
4. The user clicks the link from their inbox. `GET /api/v1/auth/oauth/confirm-link?token=...` validates the token, links the GitHub identity to the user (`github_subject` set; `password_hash` untouched; `provider` not mutated), revokes all prior active refresh tokens, and issues a fresh access JWT + refresh cookie.

### Why we do it (the threat model)

A bare 409-on-collision policy leaves an attack window open: an attacker who controls the verified email at the OAuth provider can register the same email at the application via OAuth, then claim ownership of the existing local account. Returning 409 prevents the silent merge but does not authenticate the link request — the attacker can simply retry until the local owner happens to be the one who triggered the request, or the policy is changed.

Interactive proof-of-control closes this because the link is only completed when whoever holds the inbox at the local provider clicks through. The attacker would need both a verified GitHub identity at the email AND inbox access at the local provider — which is the same trust assumption the account already lives under.

### Deliberate override of prior QA resolution

The QA workbook (`UPDATED ANVILA QA CHECK-IN_ AUTH FLOW REQUIREMENTS.xlsx`, sheet "Auth Ambiguity & Risk Log") records that TC-036 was resolved on a prior pass to return **409** (option B), citing the same account-jacking concern. AUTH-REQ-035 in the same workbook reflects that resolution: *"OAuth flow returns 409 if the email conflicts with an existing account using a different provider or password."*

This implementation deliberately supersedes that resolution with option D (interactive proof-of-control), authorized by the operator on 2026-05-17. Rationale: D closes the same attack vector that motivated B while preserving a recoverable user experience. A user who legitimately owns the local email account can complete the link in one click; option B requires them to discover a separate account-linking flow that does not yet exist in the product. Option D is also the OWASP-recommended pattern for federated identity linking.

The QA workbook should be updated to reflect this re-resolution in a follow-up ticket. The implementation matches the documentation here, not AUTH-REQ-035's verbatim text. Reviewers comparing the spec to the implementation should treat this section as the authoritative current policy.
